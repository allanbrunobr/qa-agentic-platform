# Análise crítica do qa-agentic-platform — 09/11/2026

Branch `analise-qa-agentic`, HEAD `11c19bd`. Análise somente leitura: nenhum código foi alterado, nada foi commitado e nenhuma credencial foi usada. Este arquivo é o único novo no repositório.

## Resumo executivo

O projeto tem uma base sólida para a idade. As decisões estão registradas em ADRs, o veredito é calculado de forma determinística, o e2e tem um passo negativo (quebra o app e espera `contract_violated`), a tipagem é estrita e o CI roda typecheck, testes, release gate, e2e e varredura de segredos. O job `verify` do CI (typecheck, testes e release gate) passou localmente. Os jobs `e2e` e `secrets` não foram rodados nesta análise.

O verde, porém, não cobre os riscos que mais importam:

1. **A API do runtime gerado não tem autenticação nem checagem de `Host`.** Os commits de 09/11 deram token ao control plane, mas o runtime que fica em `<repo>/.agentic-qa` (o que guarda chaves de LLM e dirige um browser) não recebeu o mesmo tratamento. Uma página aberta no navegador do desenvolvedor alcança essa API por DNS rebinding (S-01). O próprio token do control plane também vaza por DNS rebinding, porque o dashboard web o entrega a qualquer `Host` (S-15).
2. **O discovery apaga e sobrescreve arquivos fora do repositório** quando o repositório-alvo versiona um symlink dentro de `.agentic-qa/adapter`. O `SECURITY.md` promete o contrário (S-02).
3. **Há caminhos que produzem resultado de QA falso.** A URL-alvo escolhida no dashboard é ignorada pelas tools, que testam a URL do ambiente (B-02). Um passo sem artefatos é aprovado quando o modelo para sem agir, inclusive por `max_tokens` (B-03). O agente não tem como registrar um finding (B-04). Um retry que se recupera vira `contract_violated`; isso não dispara nos cenários gerados hoje (sem retry), mas dispara assim que um retry for configurado, e o estado `restricted` não tem saída (B-01).
4. **Parte dos testes não distingue o comportamento que afirma testar.** Os testes de política de risco passam mesmo sem o bloqueio (T-01). As asserções de bind em loopback testam o helper do próprio teste (T-02). 29 erros de tipo nos testes ficam escondidos (T-03).

**Recomendação:** antes de distribuir o runtime para mais repositórios, resolver os três P1 (S-01, S-02, B-02). O esforço estimado é de 2 a 3 dias de uma pessoa. Os P2 somam de 2,5 a 4 semanas e cabem nos ciclos seguintes, começando por S-15 e B-01.

## Pontos fortes (com evidência)

- **Veredito determinístico com teste negativo de ponta a ponta.** O e2e quebra o app e exige `contract_violated` (`docs/testing.md`, seção End to end; ADR 0003). É exatamente o tipo de instrumento que distingue um runtime que aprova tudo de um que funciona.
- **Política de tools aplicada na execução, não só na lista oferecida ao modelo:** `agent-runtime.ts:381` e `tool-registry.ts:40-44` recusam nome não permitido.
- **Confinamento de endpoint bem feito para a URL inicial** (`phase2/tools/endpoint-confinement.ts`): recusa `//`, `\\`, `@`, userinfo e troca de origem ou protocolo.
- **O instalador já tem o padrão certo contra symlink:** `local-package-installer.ts` usa `lstat`/`isSymbolicLink` e `realpath`. O problema de S-02 é esse padrão não ter sido aplicado ao materializer.
- **Tipagem disciplinada.** 1 ocorrência de `any` em `packages/`, 0 no runtime e na web, nenhum `@ts-ignore`. O runtime usa `strict` e `noUncheckedIndexedAccess`.
- **No runtime, o orquestrador captura exceção de hook e tool por tentativa e fecha a sessão como `failed`.** `MAX_TOOL_ROUNDS` esgotado vira falha, e não existe fallback silencioso para o provider determinístico: um provider mal configurado devolve 503 antes de criar a sessão.
- **Documentação acima da média para um projeto alfa:** arquitetura, testes, arquivos gerados e 4 ADRs.

## 2. Segurança

Modelo de ameaça considerado, o mesmo do projeto (ADR 0004 e `SECURITY.md`): (a) conteúdo do repositório-alvo é não confiável; (b) página web maliciosa aberta no navegador do desenvolvedor; (c) o app sob teste pode conter prompt injection; (d) dependências.

### S-01 · P1 · API do runtime gerado sem autenticação e sem checagem de `Host`

O runtime escuta em `127.0.0.1` e tem allowlist de CORS, mas a allowlist só deixa de enviar o header CORS: a requisição é processada mesmo assim. Nenhuma rota exige token e não existe checagem de `Host`. Com DNS rebinding, a página do atacante passa a ser *same-origin* com a API e lê e escreve tudo. Medido num servidor isolado com a mesma configuração: `Host` estrangeiro recebeu 200 em `GET` e em `PATCH` de settings. O control plane recebeu token no commit `a538a1a` (contornável, ver S-15); o runtime, que é quem guarda as chaves e dirige o browser, não recebeu nada.

**Evidência** — `templates/persona-qa-dashboard/packages/api/src/index.ts:40`
```ts
  await app.register(cors, {
    origin: (origin, callback) => {
      if (!origin || allowedOrigins.has(origin)) {
        callback(null, true)
        return
      }
```

**Evidência** — `templates/persona-qa-dashboard/packages/api/src/routes/settings.ts:25`
```ts
  app.patch('/api/settings/runtime', async (request, reply) => {
```

**Evidência (o que a documentação promete)** — `SECURITY.md:27`
```text
The generated API reflects only the local web origins, not an arbitrary browser origin.
```

- **Impacto, encadeando com outros achados:** o atacante lê `GET /api/p2/sessions/:id/events`, que contém saída de CLI e de API sem redaction (S-03, S-06). Pode disparar `POST /api/p2/runs` com `targetBaseUrl` arbitrário (S-07), gastando tokens do usuário e levando o browser a URLs internas. Pode trocar o provider, gravar personas que viram system prompt (S-14) e disparar o `pnpm` legado (A-04).
- **Recomendação:** reaproveitar `control-plane-guard.ts`: token local em arquivo `0600` injetado na página, exigido em toda rota exceto `/health`. Validar `Host` contra `127.0.0.1:<porta>` e `localhost:<porta>`. Recusar `Origin` fora da allowlist em vez de só omitir o header. Corrigir o `SECURITY.md:27`.
- **Esforço:** M (8–12 h, incluindo testes que sobem o servidor e mandam `Host` e `Origin` estrangeiros).

### S-02 · P1 · O discovery apaga e sobrescreve arquivos fora do repositório via symlink

`materializeLocalDiscovery` monta `<repo>/.agentic-qa/adapter` sem `lstat`/`realpath`. `readdir` segue um symlink de diretório, e o laço apaga todo arquivo com `.generated.` no nome. Depois, `fs.writeFile` atravessa symlinks de diretório e de arquivo. O único `realpath` do arquivo é o da raiz do repositório (linha 378). Reproduzido em repositório descartável: um arquivo `victim.generated.keep` fora do repositório foi **apagado**, 5 JSONs foram gravados fora, e `victim.txt` fora do repositório foi **sobrescrito** com o manifesto.

**Evidência** — `packages/dashboard-api/src/services/local-discovery-materializer.ts:357`
```ts
      if (!entry.isFile() || !entry.name.includes('.generated.')) return
      await fs.rm(path.join(directory, entry.name), { force: true })
```

- **Impacto:** um repositório não confiável que versione `.agentic-qa/adapter/config -> <diretório da vítima>` provoca perda de dados e escrita arbitrária no home do usuário quando alguém roda `discover-local`. Isso contradiz o `SECURITY.md` ("A write outside that directory is a bug").
- **Recomendação:** antes de qualquer IO, resolver `realpath` de cada diretório de destino e exigir que esteja dentro de `realpath(<repo>/.agentic-qa)`. Recusar symlinks com `lstat` em diretórios e arquivos. Escrever com `O_NOFOLLOW` ou gravar em arquivo temporário seguido de `rename`. Estender `hardening.regression.test.ts` com esse caso (hoje ele cobre só o symlink do `.agentic-qa` inteiro). O mesmo vale para `copyDirRecursiveIfExists` (S-14).
- **Esforço:** M (4–6 h).

O runtime executa `node <bin do package.json>` do repositório-alvo, com args escolhidos pelo modelo sem filtro e o ambiente completo do runtime. A tool é registrada com `riskLevel: 'read'`.       cwd,

- **Por que P2 e não P1, como a frente propôs:** executar o código do alvo é o propósito da tool, e um repositório malicioso já executa código de qualquer forma. O defeito corrigível é entregar segredos que o alvo não precisa e gravá-los em eventos legíveis via S-01.

### B-01 · P2 · Retry que se recupera vira `contract_violated`, e `restricted` não tem saída

Nos dois avaliadores (core e template), um passo que falhou alguma vez fica `failed` mesmo que a tentativa seguinte complete, porque `failed` tem precedência. Cada passo nessa situação soma uma violação grave. Os passos seguintes ainda são contados fora de ordem, porque `observedStepOrder` registra um `step_started` por tentativa.

**Evidência** — `templates/persona-qa-dashboard/packages/api/src/phase2/services/contract-evaluation.ts:97`
```ts

      failedStepIds.has(step.id)
        ? 'failed'
        : completedStepIds.has(step.id)
          ? 'complete'
```

**Evidência (mesma regra no core)** — `packages/core/src/runtime/contract-evaluation.ts:114`
```ts
    const status =
      failedStepIds.has(stepId)
        ? 'failed'
```

Depois de 3 vereditos assim entre as 5 últimas sessões, o gate fica `restricted` e `POST /api/p2/runs` responde 409. Nenhuma rota tira o cenário desse estado: não há expiração, override nem remoção de sessões p2. Sem execução nova, a janela nunca muda.

**Evidência** — `templates/persona-qa-dashboard/packages/api/src/phase2/services/scenario-quality-gates.ts:57`
```ts

    return {
      scenarioId,
      status: 'restricted',
```

- **Medido:** cenário `first_order_multi_role`, com a sequência de eventos montada no script no mesmo formato que o orquestrador grava. Sem retry: `contract_compliant`. Com retry recuperado no passo 0 e sessão `complete`: `contract_violated` (hardViolations=1, dois passos `outOfOrder`). Depois de 3 sessões assim: `restricted`. O orquestrador real emite esse `step_failed` antes de cada nova tentativa (`orchestrator.ts:177-180`, status `recoverable_failed`).
- **Por que P2 e não P1, como a frente propôs:** os cenários gerados pelo discovery fixam `maxAttempts: 1`, e o materializer não define `retryPolicy`. No caminho padrão não há retry, então o veredito falso não dispara hoje. Só os cenários de referência, que a documentação manda não ligar em repositório real, usam `maxAttempts: 2`. O defeito vira ativo no dia em que alguém configurar retry. A falta de saída de `restricted` vale desde já, para três violações genuínas.

**Evidência (cenários gerados não têm retry)** — `templates/persona-qa-dashboard/packages/api/src/phase2/scenarios/index.ts:123`
```ts

```

- **Impacto:** com retry configurado, resultado de QA falso (vermelho indevido) seguido de bloqueio permanente de cenários instáveis que passam no retry. Sem retry, o bloqueio permanente depois de 3 violações reais. Nos dois casos o operador só sai editando o SQLite.
- **Recomendação:** calcular o status de cada passo pela **última** tentativa, contar tentativas como sinal separado (drift, no máximo) e deduplicar `observedStepOrder`. Corrigir nas duas cópias (ver A-01). Criar saída auditada de `restricted` (override com motivo, ou expiração) e documentá-la em `docs/architecture.md`.
- **Esforço:** S (2–3 h) para o veredito + M (4–6 h) para a saída do gate.

### B-02 · P1 · A URL-alvo escolhida no dashboard é ignorada: as tools navegam para `PLAYWRIGHT_BASE_URL`

O runner cria a página com `baseURL = targetBaseUrl`, mas as tools geradas montam uma URL **absoluta** a partir de `process.env.PLAYWRIGHT_BASE_URL`, que passa por cima do `baseURL`. O README manda definir `PLAYWRIGHT_BASE_URL` ao subir o runtime, e o dashboard tem um campo "target base URL" (`Overview.tsx:122`). Com os dois definidos, o painel de auditoria mostra a URL digitada enquanto o browser testa a do ambiente.

**Evidência** — `templates/persona-qa-dashboard/packages/api/src/phase2/tools/generated-adapter-tools.ts:655`
```ts
function normalizeRouteHint(value: string | undefined): string {
  const rawRoute = !value || value === '*' ? '/' : value
  if (/^https?:\/\//i.test(rawRoute)) return rawRoute
  const route = rawRoute.startsWith('/') ? rawRoute : `/${rawRoute}`
  const baseUrl = process.env['PLAYWRIGHT_BASE_URL']
  if (!baseUrl) return route
```

- **Medido:** com tools reais e página falsa criada para o alvo `requested-target`, `openPrimaryRoute` chamou `goto('http://env-target.local:3012/dashboard')`. Nas execuções sem browser acontece o mesmo com `targetRepoPath`, que é lido do ambiente e do metadata.
- **Impacto:** o veredito é atribuído a um alvo (o preview da PR, por exemplo) que não foi testado. Pode ser verde falso ou vermelho falso.
- **Recomendação:** passar a base do run no `ToolContext` e resolver as rotas contra ela, nunca contra o ambiente. Gravar no evento a URL efetivamente navegada.
- **Esforço:** M (4–6 h).

### B-03 · P2 · Passo sem artefatos declarados é aprovado quando o modelo para sem agir, inclusive por `max_tokens`

**Evidência** — `templates/persona-qa-dashboard/packages/api/src/phase2/services/agent-runtime.ts:307`

### B-06 · P2 · Timeout de tool ou de modelo não cancela o trabalho

O deadline é só um `Promise.race`. Nenhum `AbortSignal` chega às tools Playwright nem aos providers.

**Evidência** — `templates/persona-qa-dashboard/packages/api/src/phase2/services/agent-runtime.ts:534`
```ts
      return await Promise.race([
        this.toolRegistry!.execute(toolName, input, profile.toolPolicy, toolContext),
        new Promise<never>((_, reject) => {
          timeout = setTimeout(() => reject(new ModelDeadlineExceededError(profile.timeoutMs)), remainingMs)
        }),
```

- **Medido:** uma tool de 600 ms com `timeoutMs=200` fez o passo retornar `timeout` em 201 ms, e a tool terminou e gravou 400 ms depois.
- **Impacto:** no retry, a tool órfã continua clicando e preenchendo na mesma página e grava artefatos na sessão depois do fim do passo, o que mistura evidência entre tentativas. Chamadas de modelo seguem consumindo tokens.
- **Recomendação:** um `AbortController` por passo, com o sinal no `ToolContext` e nos providers. Recriar a página antes do retry ou esperar a tool anterior terminar.
- **Esforço:** M (6–10 h).

### B-07 · P2 · Sessões ficam `running` para sempre depois de shutdown ou crash

No `SIGTERM`/`SIGINT`, o shutdown fecha o app e chama `process.exit(0)` sem marcar as sessões em andamento. Não existe reconciliação no boot nem status `interrupted`. No core, um hook que lança deixa a sessão em `running`, porque não há `try/finally` depois da linha 36. Esse último caso foi medido: o motor lança e a sessão fica `running`.

**Evidência** — `templates/persona-qa-dashboard/packages/api/src/index.ts:93`
```ts
  const shutdown = async (signal: string): Promise<void> => {
    app.log.info(`Received ${signal}, shutting down gracefully...`);
    await app.close();
    closeDb();
    process.exit(0);
```

**Evidência** — `packages/core/src/runtime/adapter-execution-engine.ts:36`
```ts
  await sessionStore.updateSession(sessionId, { status: 'running' })
```

- **Impacto:** essas sessões ficam `contract_evaluating` para sempre e **somem do gate**, que só olha `complete`/`failed`. Um teste interrompido não conta como falha.
- **Recomendação:** no boot, marcar `pending`/`running` como `failed` com o evento `run_interrupted`. No core, `try/finally` que fecha a sessão como `failed`.
- **Esforço:** S (2–4 h).

### B-08 · P2 · No motor do core, um passo que falhou pode sair como `complete`

O laço de retry é limitado por `maxRetries = 1` local, mas a decisão de desistir usa `result.maxRetries`. Se o adapter permitir 3 retries, a segunda falha sai do `while` sem marcar falha, cai no `step_completed` e a sessão termina `complete`, com os artefatos da tentativa que falhou.

**Evidência** — `packages/core/src/runtime/adapter-execution-engine.ts:93`
```ts
    const maxRetries = 1

    while (attempt <= maxRetries) {
```

**Evidência** — `packages/core/src/runtime/adapter-execution-engine.ts:159`
```ts
      const allowedRetries = result.maxRetries ?? maxRetries
      if (!(result.retryable ?? false) || attempt >= allowedRetries) {
```

- **Medido:** `maxRetries: 3`, sempre falhando: 2 tentativas, sessão `complete`. O veredito saiu `contract_violated` porque houve `step_failed`, mas o status da sessão mente.
- **Recomendação:** usar `allowedRetries` como limite do laço e falhar explicitamente quando esgotar. Adicionar teste.
- **Esforço:** S (1 h).

## 6. Riscos de entrega e recomendações priorizadas

### Riscos de entrega

1. **Distribuir o runtime como está expõe a máquina de cada usuário (S-01 + S-02, e S-15 no control plane).** O produto roda dentro do repositório e da sessão de navegador do desenvolvedor, com as chaves de LLM dele. São os riscos que mais custam se forem explorados, e as correções já têm padrão no próprio código (o guard do control plane e o `lstat` do instalador), faltando acrescentar a checagem de `Host`.
2. **Confiança no veredito.** B-02, B-03 e B-04 fazem o produto errar justamente no que vende: "o veredito significa alguma coisa". B-01 vai se juntar a eles quando o retry for habilitado. Hoje o e2e prova o caso feliz e um caso quebrado, mas não cobre URL-alvo, truncamento, finding nem retry.
3. **Instaladas não se atualizam (A-03).** Cada mês sem mecanismo de upgrade aumenta o número de cópias antigas, e o template é 70% do repositório.
4. **Testes que passam sem medir (T-01, T-02, T-03, T-04).** O verde do CI hoje dá mais confiança do que deveria em política de risco, bind e escaping.
5. **Bus factor 1.** Um único contribuidor em 120 commits, com intervalos longos (04/2026 → 06/2026 → 10–11/2026). A documentação e os ADRs reduzem esse risco, mas não o eliminam.

## Limitações desta análise

- A rodada 1 não devolveu achados estruturados (créditos esgotados). O material dela entrou neste relatório só onde havia medição ou reprodução, e cada item foi reverificado no código. Por isso, arquitetura e manutenibilidade foram avaliadas com menos profundidade do que segurança e bugs.
- Não foram cobertos a fundo: o L5 closed-loop scheduler e o self-healing; o caminho de execução `generated_non_browser`; execuções concorrentes do mesmo cenário (`POST /api/p2/runs` não limita concorrência, mas isso não foi medido); a serialização YAML dos workflow-contracts; o launcher e o `load-env` gerados, além do que o teste de hardening já cobre; o tratamento de erro dos providers diante de 429/5xx reais.
- O control plane foi revisado só em parte: o guard, a checagem de token, `Origin` e `Host` e o `GET /` do dashboard web (S-15). Ficaram de fora o escaping de todos os pontos de interpolação do `dashboard-web/src/server.ts` (1.679 linhas, que T-02 também não cobre) e a validação de caminho em cada rota que recebe `repoPath`. Não verifiquei se os 4 commits de segurança de 09/11 deixaram caminhos equivalentes sem correção, além do achado S-15.
- Cobertura de linhas não foi medida. O e2e com Chromium e o job de gitleaks não foram rodados nesta análise.
- Severidades são julgamento. P1 foi reservado a caminhos de falha fechados no código, alcançáveis na configuração padrão e reproduzidos (S-01, S-02, B-02). S-15 ficou em P2 porque o ataque exige dois rebindings e não foi reproduzido.
